## 1. Summary

健康状况模块是一套面向个人的健康记录与行为复盘工具。用户通过轻量手动记录身体、饮食、日常状态和运动训练，查看今日状态与周/月趋势，并获得一条基于自己记录、可执行但非医疗化的复盘提示。

V1 不依赖手表、手环或第三方健康平台，不提供诊断、治疗建议、疾病风险结论、精确热量推算或 AI 自动处方。产品只忠实保存用户记录、进行透明计算、展示可比较的变化。

## 3. Background

### 3.1 用户问题

现有健康应用常见两种极端：

- 依赖穿戴设备自动采集大量数据。没有设备时，核心价值明显下降。
- 要求用户每天填写复杂表单。数据虽然完整，但记录负担高，难以坚持。

用户真正需要的是一个可信、低压力的个人记录入口：

- 可以快速记下真实发生的身体和行为数据。
- 不必理解复杂健康术语，也不用每天填满所有指标。
- 能看懂“最近发生了什么变化”，而不是面对大量孤立图表。
- 数据由自己控制，可更正、撤销删除、导出和恢复。
- 系统不利用有限数据制造健康焦虑或冒充医生。

### 3.2 为什么采用 OtterLife 式方向

OtterLife 将睡眠、运动、饮水、饮食等内容集中在同一健康入口，并以低压力、游戏化陪伴降低健康工具的沉重感。Dice Life 借鉴其“一站式入口、轻量记录、趋势陪伴”思路，但不复制其穿戴设备、HRV 压力判断、宠物换装或精确能量计算。

Dice Life 的差异是：

- 没有硬件也能完整使用首版核心闭环。
- 明确区分事实记录、透明计算和系统提示。
- 不把主观或不完整数据包装成精准健康结论。
- 与 Dice Life 的个人成长档案连接，但不通过惩罚和竞争制造压力。

### 3.3 产品原则

1. **记录事实，不扮演医生**：展示输入、计算和趋势，不做诊断或治疗。
2. **少填也有价值**：用户只启用自己关心的日常指标；没有填写不视为失败。
3. **快速优先**：常用记录应在 30 秒内完成，训练中单组更新应在 5 秒内完成。
4. **比较要有条件**：只在同一项目、相同记录模式和可比较条件下描述变化。
5. **中性表达**：不用红色警报、危险评分、羞辱文案或强制连续打卡。
6. **数据属于用户**：本地优先、可导出、可恢复，不上传第三方、不用于模型训练。
7. **渐进披露**：健康首页展示摘要和入口，复杂字段进入子模块后再出现。

### 3.4 约束与假设

- V1 是单用户、本地浏览器应用。
- 用户自行输入数据，系统无法证明输入是否准确。
- 无穿戴设备同步，步数、睡眠、饮水和运动数据均由用户主动记录。
- 浏览器本地数据可能因清理站点数据、更换设备或磁盘损坏丢失，因此必须提供导出与恢复。
- 饮食照片仅保存在本地设备。

## 4. Objective

### 4.1 产品目标

1. 建立一个不依赖硬件的统一健康记录入口。
2. 让用户能够在一个月后看懂身体、日常与训练的真实变化。
3. 把每日记录成本控制在用户愿意长期承受的范围内。
4. 通过可恢复更正、来源说明和透明计算建立数据可信度。
5. 为未来可选的 AI 私人复盘顾问提供结构化、经过用户授权的数据接口。

### 4.2 非目标用户

V1 不面向以下用途：

- 需要医生持续监护、疾病管理或药物调整的人。
- 需要儿童生长、孕产、康复、专业竞技训练等专门模型的人。
- 希望用本产品替代体检、营养师、教练或医疗设备的人。
- 需要自动采集心率、血氧、HRV、血压、血糖等临床或设备数据的人。

这些用户仍可使用普通记录能力，但产品不得针对其特殊状况生成建议或风险结论。

### 4.3 成功指标

指标在真实用户测试后校准，V1 初始目标如下：

| 指标               | 初始目标 | 口径                                 |
| ------------------ | -------: | ------------------------------------ |
| 健康模块激活率     |    ≥ 55% | 首次进入后 7 天内产生至少 2 类记录   |
| 首条记录完成率     |    ≥ 75% | 打开快速记录后成功保存至少一条       |
| 常用记录中位耗时   |  ≤ 30 秒 | 身体、餐食、睡眠或饮水单次记录       |
| 训练单组记录耗时   |   ≤ 5 秒 | 已有训练项目内完成一组并开始休息     |
| 四周持续记录率     |    ≥ 25% | 连续 4 周每周至少产生 2 天记录       |
| 趋势回访率         |    ≥ 35% | 有 7 天以上数据的用户查看过周/月趋势 |
| 可选指标关闭成功率 |     100% | 关闭后首页和快速记录均不再强制显示   |
| 更正与恢复成功率   |     100% | 更正保留历史；垃圾箱内删除记录可恢复 |
| 重复或丢失记录事故 |        0 | 正常保存、迁移、导入流程不得静默丢失 |
| 医疗化提示事故     |        0 | 不输出诊断、治疗、疾病风险或处方措辞 |

不把页面停留时长、连续打卡天数、填写指标数量或“健康评分”作为核心成功指标。

## 5. Market Segments

### 5.1 想了解身体变化但没有智能硬件的人

他们会称体重、跑步或健身，但数据散落在备忘录、相册和不同应用里。需要一个手动记录也真实有效的统一档案。

### 5.2 想建立基本健康习惯但讨厌复杂打卡的人

他们关心睡眠、饮水或活动，但不想每天回答一套问卷。需要自主选择指标，快速记录，不因漏记被惩罚。

### 5.3 有减脂、增肌或体能目标的普通训练者

他们需要记录身体变化和训练表现，但不需要专业运动员级分析。需要标准化训练日志、上次数据复用和清晰趋势。

### 5.4 已经使用 Dice Life 管理个人成长的人

他们希望健康与财富、能力、任务和情绪处于同一产品结构中，并延续温和、有成长感的体验。

| 修正错误数据 | 改完后不知道原值，误删难恢复 | 修订历史、垃圾箱、导出和导入预检        |

## 7. Solution

### 7.1 方案选择

#### 方案 A：四个独立完整工具

每个子模块都有独立首页和完整功能。覆盖全面，但导航深、学习成本高、首版范围过重。

#### 方案 B：单一每日健康问卷

每天集中填写所有数据。开发简单，但强迫用户回答不关心的问题，长期记录负担最高。

#### 方案 C：统一健康首页 + 渐进披露（采用）

首页只展示今日摘要、快速操作、四类入口和一条复盘提示。用户进入子模块后才看到完整记录和趋势；日常指标可关闭。该方案兼顾一站式体验与首版简洁度。

### 7.2 核心闭环

```text
快速记录一条真实数据
  ↓
今日状态立即更新
  ↓
同类记录积累为周/月趋势
  ↓
系统生成一条基于记录的非医疗化复盘提示
  ↓
用户决定是否继续记录或调整行为
```

### 7.4 健康首页

#### 页面内容

1. 页面标题与非医疗定位短说明。
2. 今日状态卡：仅展示今天已有记录和用户启用的日常指标。
3. 主操作“快速记录”，次操作“开始训练”。
4. 四个子模块入口：身体状态、饮食记录、日常健康、运动健身。
5. 一条复盘提示：有足够数据时描述趋势；数据不足时提示如何积累可比较记录。
6. 最近记录：最多 5 条，支持进入详情、更正或删除。

#### 渐进披露规则

- 首页不直接展示四套完整表单。
- “快速记录”先选择记录类型，再显示对应最少字段。
- 系统记住上一次使用的记录类型，但不自动提交。
- 快速记录首屏优先展示“最近使用”和一键动作；时间默认当前时间，可选字段默认折叠。
- 首页明确提示“随便从一项开始”，不显示四类完成率，也不暗示四类都要每日填写。
- 用户关闭的日常指标不出现在今日卡和快速记录默认项中，仍可在指标管理中重新开启。

### 7.5 身体状态

#### 核心字段

| 字段     | 规则                                                      |
| -------- | --------------------------------------------------------- |
| 身高     | 厘米或英尺/英寸显示；内部统一保存毫米；支持历史版本       |
| 体重     | kg 或 lb 显示；内部统一保存克；必须带记录时间             |
| 体脂率   | 0–100% 之间；可为空；允许记录测量方式和备注               |
| BMI      | `体重kg ÷ 身高m²`；自动计算；只读；保存计算使用的身高快照 |
| 身体围度 | 非 V1 核心；作为 V1.1 候选，不阻塞首版                    |

#### 交互与计算规则

- 首次记录体重时若没有身高，提示先填写身高；用户也可只保存体重，此时 BMI 显示“缺少身高，暂未计算”。
- BMI 不能手工编辑。
- 身高变更只影响变更时间之后的新 BMI；旧记录保留当时身高快照，避免历史曲线被重写。
- 更正体重、体脂或身高时新增修订版本，历史详情可查看原值、修改值、修改时间和可选原因。
- 体脂趋势若混用不同测量方式，图表显示“测量方式不同，数值仅供记录比较”，不合并解释准确变化。
- V1 不用颜色给 BMI 分级，不输出“正常、肥胖、危险”等结论。仅解释计算公式和数据来源。
- 趋势支持 7 天、30 天、90 天和全部；记录少于 2 条时展示空态，不画误导性趋势线。

### 7.6 饮食记录

#### V1 字段

- 餐次：早餐、午餐、晚餐、加餐、其他。
- 时间：默认当前时间，可修改。
- 内容：自由文字，最多 500 字。
- 照片：最多 3 张，可为空。
- 主观饱腹：未选择、偏少、刚好、偏饱、很撑。
- 备注：最多 300 字，可为空。

#### 规则

- 文字和照片至少填写一项。
- 不提供食物数据库、条码扫描、热量计算、营养素估算或饮食诊断。
- 不把“很撑”标红，也不评价一餐“健康/不健康”。
- 照片在本地压缩后保存；原图不上传。
- 今日页按时间线展示餐次；周/月页展示记录天数、餐次数和饱腹选择分布，不推断营养质量。
- 后续 AI 若分析饮食，必须由用户明确发起并单独授权对应记录，不在 V1 自动执行。

### 7.7 日常健康

#### 可选指标

| 指标 | 输入方式                                   | 默认状态 | 趋势表达                     |
| ---- | ------------------------------------------ | -------- | ---------------------------- |
| 睡眠 | 入睡/起床时间或直接输入时长；质量 1–5 可选 | 开启     | 平均时长、记录天数、质量分布 |
| 饮水 | 快捷杯量或自定义 ml                        | 开启     | 每日总量、记录天数           |
| 活动 | 步数或活动分钟二选一为主要模式             | 开启     | 每日值、周累计、记录天数     |
| 精力 | 1–5 级，可跳过                             | 关闭     | 分布与自我变化，不解释原因   |

#### 规则

- 用户可关闭任一指标；关闭不删除历史数据。
- 没记录不等于零。趋势计算必须区分“0”和“缺失”。
- 饮水快捷项允许自定义常用杯量；系统不默认计算“你每天必须喝多少水”。
- 久坐提醒、喝水定时提醒不进入 V1。V1 只记录，不进行操作系统级推送。
- 睡眠跨午夜时自动计算时长；若结束时间早于开始时间，默认视为次日并明确展示日期。
- 睡眠超过 24 小时、饮水单次超过 5 L、步数超过 200,000 等极端值不直接拦截，弹出中性复核提示后允许用户确认保存。
- 精力仅代表用户当时自评，不与睡眠、饮食建立因果关系。

### 7.8 运动健身

#### 训练项目模型

用户自定义项目名称，并选择一种标准记录模式：

| 记录模式 | 适用示例             | 必填数据       | 系统派生数据           |
| -------- | -------------------- | -------------- | ---------------------- |
| 距离计时 | 跑步、骑行、游泳     | 距离、用时     | 配速、平均速度         |
| 重量次数 | 卧推、深蹲、器械训练 | 每组重量、次数 | 最佳组、总次数、训练量 |
| 自重次数 | 俯卧撑、引体向上     | 每组次数       | 单组最高、总次数       |
| 定时组数 | 平板支撑、靠墙静蹲   | 每组持续时间   | 最长组、总时长         |
| 时长训练 | 瑜伽、拉伸、球类     | 总时长         | 周次数、累计时长       |

为覆盖真实训练但不增加默认负担，各模式提供折叠的高级字段：

- 距离计时：可选分段距离与分段用时。
- 重量次数：可选组类型（热身、正式、递减）、单侧标记。
- 自重次数：可选额外负重或辅助重量、单侧标记。
- 定时组数：可选单侧标记。
- 所有高级字段均可不填，不阻塞最小记录。

创建字段只有：项目名称、记录模式、显示单位、可选默认休息时长。用户不填写“进步方向”，系统按模式展示可比较指标，但不把单一数字自动等同于整体体能。

#### 训练流程

1. 点击“开始训练”或“快速补录”。
2. 新训练可从空白开始、复制上次训练，或选择保存的训练模板。
3. 训练中添加自定义项目。
4. 力量、自重和定时项目按组记录；完成一组后勾选。
5. 若项目设置休息时长，勾选后自动启动倒计时；到点使用页面内声音/震动（浏览器允许时）和视觉提示。
6. 用户可暂停、跳过或延长休息；实际休息时间可记录但不必手填。
7. 结束训练时显示摘要，允许补充备注并保存。

#### 记录效率

- 默认展示上一次同项目记录，但清楚标注“上次”，不当作本次已完成。
- 支持一键复制上次训练、复制上一组、修改后勾选。
- “快速补录”允许训练后一次输入摘要；重量次数等仍保留逐组结构，不压成一个总数。
- 未结束的训练自动保存草稿；重新进入时询问继续或放弃。

#### 进步与纪录表达

- 相同距离用时更短：描述为“本次该距离用时减少”。
- 更长距离：描述为“最长距离记录”，不直接称体能提升。
- 相同次数下重量更高：描述为“该次数下最高重量”。
- 相同重量下次数更多：描述为“该重量下单组次数提高”。
- 总训练量增加：只描述训练量变化，不等同于力量增长。
- 训练条件不相同或数据不足：不生成“进步/退步”判断。
- 运动消耗卡路里不进入 V1，因为没有可靠传感器和个体参数时精确度不足。

### 7.9 今日状态、趋势与复盘提示

#### 今日状态

今日状态是已有记录摘要，不是健康评分：

- 身体：最近一次体重、体脂和 BMI（注明记录日期）。
- 饮食：今日已记录餐次数。
- 日常：仅展示启用指标的今日值或“未记录”。
- 运动：今日训练状态、时长或主要结果。

#### 趋势

- 趋势范围：周、月和自定义 90 天。
- 默认按单一指标展示，不用一个综合分数混合不同数据。
- 缺失日留空，不补零、不插值。
- 图表下方同时提供文字摘要，保证不依赖颜色或图形理解。
- 比较周期数据覆盖不足 50% 时，明确显示“记录较少，暂不比较周期变化”。

#### 复盘提示引擎

V1 使用固定白名单模板，不调用 AI，不允许组件自由拼接健康建议。每次最多展示一条，并同时提供“查看依据”入口，列出所用记录及时间。优先级如下：

1. 数据安全：长期未导出时提醒备份。
2. 数据质量：发现极端值、混合测量方式或可比较数据不足。
3. 记录连续性：指出还差多少条记录可以形成趋势。
4. 已观察变化：中性描述可比较指标的变化。
5. 下一步行动：建议“记录、复核、查看趋势或继续既有计划”，不建议治疗、补剂或具体饮食处方。

合格示例：

- “本月已有 4 次体重记录，可以查看 30 天趋势。”
- “本周记录了 3 次睡眠。再记录 2 次，会更容易看出自己的作息变化。”
- “本次 5 公里用时比上次同距离少 52 秒。”
- “两次体脂记录使用了不同测量方式，建议分开理解数值。”

禁止示例：

- “你的睡眠不足，会导致免疫力下降。”
- “BMI 偏高，存在肥胖风险。”
- “今天应摄入 1800 千卡并补充维生素 D。”
- “你的压力很高，建议就医。”

模板禁用判断词包括但不限于：“正常、异常、健康、不健康、疾病风险、应该摄入、治疗、处方”。若产品以后要增加模板，必须通过提示语料测试和医疗化措辞审查。

页面固定提供：“本模块用于个人记录与复盘，不提供诊断、治疗或医疗风险判断。明显不适请联系专业人员。”

### 7.10 详细用户故事与验收标准

#### US-01 首次进入与自主配置

作为首次使用者，我希望只选择自己关心的日常指标，以免每天面对无关字段。

验收标准：

1. 首次进入可直接使用，不强制完成冗长问卷。
2. 默认开启睡眠、饮水、活动；精力默认关闭。
3. 用户可关闭所有日常指标，身体、饮食和运动仍可独立使用。
4. 关闭指标不会删除已有记录。
5. 设置可随时修改并立即反映到首页与快速记录。

#### US-02 记录身体数据

作为用户，我希望记录体重和体脂，并让系统自动计算 BMI。

验收标准：

1. BMI 字段只读，计算公式准确。
2. 缺少身高时允许保存体重，但不计算 BMI。
3. 所有单位明确显示，切换单位不会改变内部真实值。
4. 更正记录产生修订历史，不静默覆盖。
5. 只有一条数据时不显示趋势结论。

#### US-03 轻量记录一餐

作为用户，我希望用文字或照片快速记下一餐，而不用查食物库和卡路里。

验收标准：

1. 文字和照片至少一项即可保存。
2. 保存后立刻出现在今日餐次时间线。
3. 不显示热量、三大营养素或健康评分。
4. 照片不产生外部网络上传请求。
5. 删除后进入垃圾箱，可恢复原记录和照片关联。

#### US-04 记录睡眠

作为用户，我希望输入入睡和起床时间，系统自动算出时长。

验收标准：

1. 正确处理跨午夜睡眠。
2. 可改为直接输入时长。
3. 睡眠质量可跳过。
4. 极端值经中性复核后仍可保存。
5. 缺失日不按 0 小时统计。

#### US-05 快速记录饮水

作为用户，我希望点击常用杯量快速累计今日饮水。

验收标准：

1. 支持至少 3 个可编辑快捷杯量。
2. 每次点击生成独立记录，可撤销最近一次。
3. 今日总量由记录累加，不能直接覆盖来源明细。
4. 不显示强制每日目标或“未达标”警报。

#### US-06 创建训练项目

作为训练者，我希望自定义项目名称并选择合适的记录模式。

验收标准：

1. 必须选择五种标准模式之一。
2. 不要求填写进步方向。
3. 保存后不能直接改变记录模式；需要新建项目或通过明确迁移流程转换，避免历史结构损坏。
4. 同名项目允许存在，但创建时提示用户区分。

#### US-07 逐组训练

作为力量训练者，我希望复制上次训练并逐组记录，减少输入。

验收标准：

1. 能复制上次同一训练的项目和组数据。
2. 复制数据默认处于未完成状态。
3. 勾选一组后可自动开始休息倒计时。
4. 离开页面再返回时，未结束训练可恢复。
5. 保存后每组重量、次数、完成时间和顺序均保留。

#### US-08 查看趋势

作为用户，我希望知道记录发生了什么变化，但不被系统吓唬。

验收标准：

1. 图表与文字摘要展示同一结论。
2. 数据不足时说明不足，不生成趋势方向。
3. 缺失值不补零。
4. 不出现诊断、疾病风险、治疗或羞辱性措辞。
5. 颜色不是传达增加、减少或异常的唯一方式。

#### US-09 更正、删除与恢复

作为用户，我希望修正错误且能撤回误删。

验收标准：

1. 更正保留原值与修订时间。
2. 普通删除进入垃圾箱，不立即物理清除。
3. 垃圾箱支持单条恢复和明确确认后的永久删除。
4. 恢复后记录回到原日期和原关联位置。
5. 永久删除照片时一并清除本地媒体对象。

#### US-10 导出与恢复

作为用户，我希望把健康数据备份到自己的文件中。

验收标准：

1. 可导出带版本号、时间和校验信息的数据包。
2. V1 导出为单文件 JSON bundle，包含结构数据、媒体编码、manifest 清单和 checksum 校验和。
3. 导入前完整预检版本、文件数量、ID 唯一性、引用与校验和，并展示记录与媒体摘要。
4. V1 不做逐条合并；用户明确确认后整体替换，替换失败事务回滚，不静默覆盖当前数据。
5. ZIP 与按实体 `updatedAt` 处理分叉冲突的逐条合并延后到 V1.1。
6. 不支持的未来版本拒绝导入并保留现有数据。
7. 导入失败不改变当前数据。

- 媒体对象必须有唯一所有者；永久删除所有者后清理孤立媒体。
- 导入失败不得产生半完成状态。

### 7.12 本地存储、迁移与隐私

#### 存储策略

- 结构化健康数据通过独立存储适配器保存，业务组件不直接操作浏览器存储。
- 小型结构化数据可使用带版本的本地存储；照片使用 IndexedDB，避免占满 `localStorage`。
- 照片上传前在本地压缩，最长边不超过 1600px，优先 WebP；压缩失败时给出明确错误，不丢失其他表单内容。
- 所有写入采用“准备新状态 → 校验 → 原子替换”的方式，失败时保留旧状态。
- 结构化状态保留“当前状态”和“上次有效快照”，两者均附带校验和；启动时当前状态损坏则只读恢复有效快照并明确通知用户。
- 在浏览器支持时请求持久存储权限；界面必须说明浏览器可能拒绝，不能把请求成功描述为绝对不丢失。

#### 数据键与版本

- 健康结构化数据键：`dice-life.health-system.v1`。
- 媒体数据库：`dice-life-health-media`。
- 状态内必须包含 `schemaVersion`，不能仅依赖存储键判断版本。

#### 迁移

- 当前代码没有正式健康数据，V1 首次创建空状态。
- 若检测到历史原型数据，只在字段可明确映射时提供一次性导入预览；不猜测单位或记录含义。
- 迁移前保存原始快照，迁移成功并校验记录数量后才替换。
- 迁移失败时继续使用原状态，并提示用户导出诊断文件；不得自动清空。

#### 导出与导入

- V1 默认导出单文件 JSON bundle，其中包含结构化状态、媒体的 Data URL 编码、manifest 清单、版本、导出时间与 checksum 校验和。
- 导出文件由用户主动下载到本机，不发送到服务端。
- 导入先在临时区完整预检版本、文件数量、ID 唯一性、校验和与引用完整性，并展示结构记录数、媒体数和更新时间摘要。
- V1 不支持逐条合并。用户明确确认后才整体替换当前健康数据；正式替换过程中任一结构或媒体写入失败都必须事务回滚。
- 损坏、不完整、未来版本或预检失败的 bundle 直接拒绝，现有正式数据不发生改变；不得静默覆盖。
- ZIP 容器、按实体 `updatedAt` 识别分叉以及“保留本地/导入版本/两者均保留”的逐条冲突处理延后到 V1.1。

#### 隐私

- 健康数据、照片、导出内容不发送给第三方分析、广告或模型服务。
- 健康数据不用于模型训练。
- 不记录表单具体值到控制台、遥测或错误上报。
- V1 不接入 AI。未来 AI 必须由用户单次明确发起，展示将发送的字段并获得授权；默认最小化传输。
- 设置页清楚解释本地数据可能随浏览器清理而丢失，并提供导出入口。

### 7.13 异常、空态与边界条件

| 场景                  | 产品行为                                      |
| --------------------- | --------------------------------------------- |
| 首次进入无数据        | 展示四入口和“从一条记录开始”，不展示空白图表  |
| 某指标只有一条        | 显示当前值和日期，不描述趋势                  |
| 周期覆盖不足 50%      | 显示记录覆盖率，不比较周期升降                |
| 体重有值但无身高      | 保存体重，BMI 显示暂未计算                    |
| 身高在历史中变化      | 旧 BMI 保留旧快照，新记录使用新身高           |
| 体脂方法混用          | 趋势标注方法差异，不合并给出结论              |
| 重复快速点击保存      | 使用提交锁和幂等 ID，最多生成一条记录         |
| 刷新训练页面          | 恢复训练草稿和休息计时的剩余状态              |
| 浏览器不允许声音/震动 | 保留视觉倒计时，不把提醒能力描述为已开启      |
| 照片过大或格式不支持  | 保留文字表单，提示删除/更换照片后重试         |
| 本地空间不足          | 停止新写入，保留旧数据，提示导出和清理媒体    |
| 导入文件损坏          | 拒绝导入并列出校验问题，不改变当前数据        |
| 未来版本数据          | 只允许导出，不降级覆盖；提示升级应用          |
| 跨时区或系统时间改变  | 存 UTC 时间和原始时区偏移，按用户当前时区展示 |
| 删除项目仍有历史      | 归档项目，不删除历史训练                      |
| 两个同名训练项目      | 允许，但创建时提示并展示记录模式帮助区分      |

### 7.14 响应式设计

#### 桌面端（≥ 1024px）

- 延续现有固定顶部栏和左侧导航。
- 主内容保持单一纵向仪表盘，不改造成强制三栏。
- 首页今日状态与复盘提示可双列；四入口最多四列。
- 子模块列表与详情可使用主次双列，但主操作始终处于视觉首位。

#### 平板（768–1023px）

- 四入口变为两列。
- 图表和历史列表改为单列或可横向滚动的局部区域。
- 训练中组记录保持表格语义，但每组可折叠为卡片。

#### 手机（320–767px）

- 所有内容单列；固定导航不得遮挡主内容。
- 快速记录使用全屏抽屉或页面，不用窄小弹窗。
- 训练组输入使用大触控目标，数字键盘匹配字段类型。
- 主要操作按钮触控区域至少 44×44 CSS px。
- 图表提供可读文字摘要，避免用户必须横向拖动才能理解。

### 7.15 键盘与 WCAG

目标为 WCAG 2.2 AA：

- 所有功能可仅用键盘完成；Tab 顺序与视觉顺序一致。
- 页面、抽屉、对话框有明确标题；打开后焦点进入，关闭后回到触发按钮。
- Escape 可关闭非破坏性对话框；有未保存输入时先确认。
- 按钮、图标按钮、图表和输入框有可理解的名称。
- 错误信息通过文字关联具体字段，不只依赖颜色。
- 前景与背景对比度满足 AA；焦点环清晰可见。
- 动画遵循 `prefers-reduced-motion`，休息计时不依赖动画表达剩余时间。
- 趋势图提供数据表或文字摘要；屏幕阅读器可获得指标、时间范围、最大/最小和记录数量。
- 单位不会只放在 placeholder 中；输入值与单位可被辅助技术共同读取。
- 保存成功、撤销、计时结束等状态通过非打断式 `aria-live` 通知。
- 日期和时间输入提供文本标签与格式示例。

### 7.16 技术边界与未来 AI 接口

V1 领域层分为：

1. 记录与校验：创建、更正、软删除和恢复。
2. 派生计算：BMI、时长、配速、训练量和趋势覆盖率。
3. 复盘规则：只消费脱敏后的结构化摘要，不直接读取组件状态。
4. 存储适配器：结构化状态、媒体、导入导出。
5. UI：健康首页和四个子模块。

为未来 AI 预留只读顾问接口，但 V1 不调用：

```ts
type HealthAdvisorSnapshot = {
  generatedAt: ISODateTime;
  selectedScopes: Array<"body" | "meals" | "daily" | "workouts">;
  dateRange: { from: string; to: string };
  summaries: unknown[];
  provenance: Array<{ recordId: string; recordedAt: ISODateTime }>;
};
```

约束：

- 必须由用户选择范围和时间段。
- 默认不含照片、自由文本和已删除记录。
- 输出建议必须引用所依据的记录，不得声称诊断。
- 专业教练 Skill 属于后续独立评审范围，不随 V1 上线。

### 7.17 分期

#### V1.0：可信记录闭环

按可独立验证的内部里程碑交付，但最终作为同一健康模块发布：

1. **基础与身体状态**：健康首页、快速记录框架、身体数据、BMI、趋势、修订历史。
2. **日常健康**：睡眠、饮水、活动、精力、指标开关。
3. **轻量饮食**：餐次、文字、照片、饱腹感、时间线。
4. **运动健身**：五种记录模式、逐组记录、复制上次训练、休息计时、补录。
5. **复盘与数据安全**：周/月趋势、一条规则提示、垃圾箱、导出导入、隐私说明。

每个里程碑必须可独立运行和验收；开发中可通过功能开关隐藏未完成入口。V1 对外发布门槛：五个里程碑全部达到本 PRD 的安全、数据和可访问性验收标准。

#### V1.1 候选

- 自定义身体围度。
- 更灵活的训练模板与超级组标记。
- 本地通知或 PWA 提醒。
- CSV 轻量导出。

#### V2 候选

- 用户主动授权的 Apple Health、Health Connect 或华为健康导入。
- 食物数据库和营养信息，但必须先验证数据来源、误差表达与记录成本。
- 用户主动发起的 AI 复盘顾问。
- 跨设备加密同步。

### 7.18 首版非目标

- 穿戴设备、手机传感器或第三方健康平台同步。
- 心率、HRV、血氧、血压、血糖、经期或医疗检验分析。
- 食物数据库、条码、拍照识别热量、宏量营养素精确估算。
- 个性化减脂热量处方、膳食计划、补剂建议。
- 医疗诊断、治疗建议、疾病风险评分或异常报警。
- AI 自动处方、后台自动分析或未经授权的数据上传。
- 社交动态、排行榜、挑战赛、教练监控和付费课程。
- 用连续打卡、扣分、角色受伤或红色警报惩罚用户。
- 运动卡路里估算和综合“健康分”。

### 7.19 风险与缓解

| 风险                         | 缓解措施                                                     |
| ---------------------------- | ------------------------------------------------------------ |
| 四个子系统导致首版过重       | 统一底层记录能力，按里程碑开发；首页渐进披露；非核心功能后移 |
| 手动记录难以坚持             | 自选指标、记住上次选择、快捷杯量、复制上次训练、补录         |
| 提示被理解为医疗建议         | 规则白名单、禁用措辞测试、固定定位说明、无健康评分           |
| BMI/体脂误导                 | BMI 只读透明计算；体脂标注测量方式；不做颜色分级和风险结论   |
| 本地数据被浏览器清理         | 显著导出入口、备份提示、导入预检、存储失败保护               |
| 照片占满本地空间             | 本地压缩、数量与尺寸限制、媒体占用展示和清理入口             |
| 训练模式覆盖不足             | 自定义名称 + 五种标准模式；真实场景测试；不强行支持复杂编排  |
| 数据更正破坏趋势             | 修订历史、身高快照、软删除、趋势排除删除记录                 |
| 主观精力与其他数据被误作因果 | 默认关闭；只展示分布；禁止自动相关性结论                     |

### 7.20 Kill Criteria

以下条件触发停止、缩减或改版，而不是继续堆功能：

1. **记录负担失败**：可用性测试中超过 40% 用户无法在 30 秒内完成一次常用记录，先重做快速记录，不增加新指标。
2. **四模块认知过载**：超过 30% 测试者首次进入后无法说清四入口区别，改为更强的首页引导或缩减首发入口。
3. **医疗误解**：任一轮测试中超过 10% 用户认为提示是医疗建议，立即停止提示上线并重写表达与边界。
4. **数据可信度失败**：发生任何可复现的静默丢失、重复写入或导入覆盖事故，阻止发布，优先修复存储层。
5. **训练模型覆盖失败**：目标用户的真实训练中超过 20% 无法被五种模式表达，暂停训练模块发布并评估最小扩展模式。
6. **趋势无价值**：有 4 周记录的用户中，少于 20% 能从趋势页说出一条可验证变化，重做趋势摘要而不是增加图表。
7. **照片成本失控**：中等设备上 50 张餐食照片导致明显卡顿或导出失败，首发降级为文字记录并推迟照片。

## 8. Release

### 8.1 发布策略

- 使用独立分支和 worktree 开发，不合入 `main`，不推送远端。
- 各里程碑均以可运行、可测试状态收口，不在主 App 中留下半完成入口。
- 健康入口完成集成前保持现有占位页，直到基础记录和存储安全通过测试。

### 8.2 发布验证

发布候选必须通过：

- 领域计算单元测试：BMI、跨午夜睡眠、单位换算、趋势覆盖率、训练派生指标。
- 存储测试：幂等保存、迁移、软删除、恢复、导入失败回滚、媒体引用完整性。
- 组件测试：快速记录、指标开关、身体更正、餐食记录、训练草稿和休息计时。
- 集成测试：主导航进入健康模块，其他财富、任务和情绪页面不回归。
- 可访问性测试：键盘流程、焦点管理、名称、对比度和自动化 axe 检查。
- 响应式人工检查：320px、768px、1024px 和桌面宽度。
- 隐私检查：记录和照片不产生外部上传；错误日志不含健康值。
- 完整测试与生产构建通过。
- 至少 5 名目标用户完成首页理解测试；超过 70% 能正确区分四入口，且不会认为四类都必须每天填写。
- 至少 20 条真实训练日志完成数据模型演练；无法表达主要结构的比例不超过 20%。
- 提示模板盲测中，把提示误解为医疗建议的用户不超过 10%。

### 8.3 上线后观察

- 首条记录完成率和常用记录耗时。
- 用户主动关闭的指标分布。
- 导出使用率与导入失败率。
- 被更正记录比例，用于发现输入设计问题。
- 训练模式未覆盖反馈。
- 用户是否误解复盘提示为医疗建议。

### 8.4 当前开放问题

普通产品取舍已由总控授权按推荐方案决定。以下问题不阻塞 V1，但需要通过测试获得证据：

- 用户是否愿意在没有热量反馈时持续记录饮食。
- 手动睡眠与活动数据是否能形成足够稳定的周趋势。
- 餐食照片的价值是否足以抵消存储和导出复杂度。
- 五种训练模式对普通用户真实训练的覆盖率。
- 一条复盘提示能否比更多图表更有效地帮助用户理解变化。
